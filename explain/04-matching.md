# Частина 1. Зрівнювання

## Проблема

Уяви, що робиш перевірку без зрівнювання.

```
пряме ребро (k = 4.0)   кореляція 0.923
конфаундер              кореляція 0.757
```

Питаєш метод: де тут справжнє ребро. Він відповідає правильно.

Здається, перемога. Але подивись **чому** він угадав. Він не розібрався в структурі — він просто взяв **більше число**. Дай йому конфаундер із сильним коренем, і кореляція стане `0.95`, а він назве ребром саме його.

Тобто ми виміряли не «чи розуміє метод причинність», а «чи вміє метод порівнювати два числа».

## Розвʼязання

Підбираємо силу прямих ребер так, щоб **обидва типи пар мали однакову кореляцію**.

Реальні числа для конфаундера, зерно `0`:

```
було  (k = 4.0)    пряме 0.923   конфаундер 0.757    легко
стало (k = 1.577)  пряме 0.757   конфаундер 0.757    величина не допомагає
```

Тепер метод **не може** виграти на величині. Єдиний спосіб — використати структуру: подивитись на третій ген, помітити, що звʼязок зникає при обумовленні.

Це називають **matched-pair design** — узгоджений парний дизайн. Ідея стара, з клінічних досліджень: щоб перевірити ліки, порівнюють хворих однакового віку, статі й тяжкості, а не будь-кого з будь-ким.

## Як влаштований підбір

`src/sim/grid.py`, функція `tune`:

```python
target = mean([strength(structure, s, k=1.0, "S") for s in seeds])
for _ in range(30):
    mid = 0.5 * (lo + hi)
    got  = mean([strength(structure, s, k=mid, "D") for s in seeds])
    lo, hi = (mid, hi) if got < target else (lo, mid)
```

Це **двійковий пошук**. Пояснюю на прикладі вгадування числа.

Я загадав число від `0` до `100`. Ти називаєш `50`, я кажу «більше». Ти називаєш `75`, я кажу «менше». Ти називаєш `62`. За сім кроків знайдеш будь-яке число зі ста.

Тут те саме, тільки замість «більше-менше» — «кореляція прямих пар вийшла слабша чи сильніша за цільову».

Цільове значення для конфаундера — `0.7568`, це середня сила структурних пар по трьох зернах при `k = 1.0`.

```
проміжок [0.05, 8.0]
крок 1   k = 4.03   кореляція 0.923   забагато    беремо ліву половину
крок 2   k = 2.04   кореляція 0.803   забагато    ліву
крок 3   k = 1.04   кореляція 0.681   замало      беремо праву
...
крок 30  k = 1.577  кореляція 0.757   збіглось
```

Перевірка на робочому зерні `0`: прямі пари `0.7570`, структурні `0.7566`. Різниця — чотири десятитисячні.

Тридцять кроків звужують проміжок від `[0.05, 8.0]` у мільярд разів. Точність надлишкова, але це дешево.

**`seeds=(101, 102, 103)`** — підбір робиться на **трьох окремих наборах даних**, і береться середнє. Інакше `k` підлаштувався б під випадковість одного набору.

**Критично:** ці зерна — `101, 102, 103` — **не збігаються** з робочими зернами `0…19`. Якби збігались, ми б підганяли коефіцієнт під ті самі дані, на яких потім міряємо. Це називають **витоком** — коли інформація про тестовий набір потрапляє в налаштування.

## `_CACHE` і чому підбір не гальмує

```python
key = (structure, tuple(sorted(cfg.items())), hide, link, rho, ckey(counts_kw))
if key in _CACHE:
    return _CACHE[key]
```

Кожен підбір — це `30 × 3 = 90` побудов панелі. Для восьми структур у чотирьох режимах вийшло б багато. Тому результат кладеться в словник за ключем із усіх параметрів.

`ckey` перетворює словник налаштувань лічильників на щось, що можна покласти в ключ словника (`dict` у Python не можна використовувати як ключ, бо він змінний).

## Коли зрівнювання **неможливе**

Тут я одного разу помилився й довелось переробляти.

```
структура     кореляція структурної пари (k = 1.0, зерно 0)
FFL                 0.820
зворотний           0.789
ланцюг              0.780
конфаундер          0.755
два приховані       0.730
надлишковий OR      0.460
колайдер            0.011      ← майже нуль
синергія AND        0.019      ← майже нуль
```

Для колайдера й `AND` структурна пара **за побудовою** не корелює. Спроба зрівняти прямі пари з нулем зробила б прямі ребра **невидимими**, і панель перетворилась би на купу шуму.

Тому в коді зʼявився `SPEC` — окремий припис для кожної структури:

```python
"confounder": {"pos": "D", "neg": "S", "correct": "high", "match": True}
"collider":   {"pos": "S", "neg": "N", "correct": "0.5",  "match": False}
```

Читається так:

- Для конфаундера порівнюємо `D` проти `S`, правильна відповідь «високо», зрівнювання **потрібне**.
- Для колайдера порівнюємо `S` проти `N` — структурну пару проти двох випадкових генів, правильна відповідь `0.5`, зрівнювання **не має сенсу**.

І `tune` для другого випадку просто повертає сталу:

```python
if not SPEC[structure]["match"]:
    return 1.6, None
```

## Найважливіше застереження: чим саме зрівнювати

Наш `tune()` рівняє **кореляцію**. Але міряємо ми й іншими методами — взаємною інформацією, наприклад.

Ми перевірили, що буде, якщо зрівняти за взаємною інформацією замість кореляції. Результат виявився сильнішим за все інше в проєкті.

На стовпці «прихований регулятор», який **нерозвʼязний за побудовою** (правильна відповідь рівно `0.5`):

```
зрівняно за     кореляція   взаємна інф.   часткова кор.   ARACNe
кореляцією        0.430        1.000          0.545         1.000
взаємною інф.     0.000        0.454          0.000         0.454
```

Ті самі дані. Ті самі методи. Змінилась лише статистика, яку зрівняли.

Зліва — **ідеальна одиниця на задачі, що не має розвʼязку**. Справа — рівно шанс, як і має бути. І кореляція внизу зліва дає `0.000`, тобто стовідсотково перевернуту відповідь.

**Правило: зрівнювати треба в тій самій статистиці, якою міряєш.** Інакше ти міряєш власне зрівнювання.

Повний розбір із усіма таблицями — у файлі `08`, частина `2`.

Практичний наслідок для нашого коду: `grid.py` поки вміє рівняти лише кореляцію. Перенести туди другий режим — пункт у списку роботи.

# Частина 2. Підлога

## Що це

**Підлога** — це число, яке метод отримає, **навіть якщо нічого не розуміє**, а просто пощастило.

Аналогія: кидаєш монету сто разів. Очікуєш `50` орлів, але вийде `47` чи `53`. Це не означає, що монета крива. Це означає, що ста кидків замало, щоб побачити точну половину.

Так само тут. У нас `25` прямих пар і `25` структурних, тобто `625` порівнянь. **Випадковий** метод дасть не рівно `0.5`, а щось у діапазоні.

## Чому саме тут вона не `0.5`

Тонкість, яку легко пропустити. Зрівнювання робиться на **середньому** по трьох зернах. Але на **конкретному** зерні `0` середні виходять трохи різні:

```
пряме ребро     0.7570
конфаундер      0.7566
різниця         0.0004
```

Різниця мікроскопічна, але **систематична** — вона в один бік. Метод, що просто читає кореляцію, отримає трохи більше половини.

Саме це й міряє `floor.py`: не «чи є різниця», а «яку `AUROC` дасть різниця такого розміру при такому розкиді».

## Як ми міряємо підлогу

Файл `floor.py`. Формула:

```
підлога = Φ(Δ / (σ · √2))
```

- `Δ` — систематична різниця середніх між типами пар
- `σ` — розкид усередині типу
- `Φ` — функція нормального розподілу, перетворює «на скільки стандартних відхилень» у «з якою ймовірністю»
- `√2` зʼявляється, бо порівнюємо **дві** випадкові величини, і їхні розкиди складаються

Виміряне:

`out/floor.json`, двадцять зерен:

```
стовпець                   Δ середніх      sd      підлога
1 спільна причина           +0.00027    0.00540    0.5143
2 прихований регулятор      +0.00107    0.00511    0.5590
3 колайдер                  +0.00113    0.00877    0.5363
4a ланцюг, B видно          +0.00099    0.00509    0.5549
4b ланцюг, B приховано      +0.00075    0.00503    0.5420
```

Дивись на колонку `Δ`: різниці порядку **однієї тисячної**. Мізерні. Але `sd` теж мале, і відношення дає підлогу помітно вище за `0.5`.

## Як це читати

```
метод дав 0.446   ← НИЖЧЕ підлоги, метод систематично помиляється
метод дав 0.530   ← на рівні підлоги, метод не робить нічого
метод дав 1.000   ← значно вище, метод справді працює
```

Кореляція в наших вимірах сидить **рівно на підлозі**. Тобто вона не «трохи гірша за інші методи» — вона **взагалі не несе інформації** про причинність. Її число цілком пояснюється залишковою похибкою зрівнювання.

Без виміряної підлоги ми б написали «кореляція дає `0.446`, що трохи гірше за випадок» — і це було б беззмістовно.

# Частина 3. Стеля

## Що це

**Стеля** — це найкращий результат, якого досягає **проста** модель. Складна модель мусить її перевершити, інакше вся складність марна.

Аналогія: нову вантажівку порівнюють не з нулем, а зі старою вантажівкою. Якщо нова возить стільки ж — вона не потрібна.

## Наша стеля

Задача моделі — **передбачити прихований ген за рештою**. Проста модель — **лінійна регресія**, тобто зважена сума інших генів:

```
передбачення = w₁·ген₁ + w₂·ген₂ + ... + b
```

Ваги `w` підбираються так, щоб помилка була найменшою. Ніяких нелінійностей, ніякої уваги.

```
завжди передбачати середнє     MSE 1.0000    базовий рівень
лінійна регресія               MSE 0.5019    СТЕЛЯ
наш трансформер                MSE 0.4113    на 18% краще
```

**MSE** — mean squared error, середня квадратична помилка: береш різницю між передбаченим і справжнім, підносиш до квадрату, усереднюєш. Квадрат потрібен, щоб плюси й мінуси не гасили один одного.

## Чому це важливо саме для нас

Якби трансформер дав `0.50`, ми б **не мали права** інтерпретувати його увагу. Бо він тоді робить те саме, що зважена сума — а в зваженій сумі немає внутрішньої структури, яку варто розглядати. Уся інформація в самих вагах.

`0.4113` проти `0.5019` означає, що модель знайшла **щось нелінійне**. Це і є перепустка до інтерпретації.

## Порядок дій, який із цього випливає

```
1  побудуй дані             знаєш правильну відповідь
2  зрівняй пари             метод не виграє на величині
3  зміряй підлогу           знаєш рівень випадковості
4  зміряй стелю             знаєш рівень простої моделі
5  ТЕПЕР міряй метод        число має сенс
```

Кроки `3` і `4` пропускають найчастіше. Саме тому в полі повно результатів, які виглядають переконливо, а насправді сидять на підлозі.

## Що ми ще не зміряли

Чесно: підлогу ми міряли для **старої** трьохстовпцевої версії стенда. Для восьми нових структур із `grid.py` підлоги **ще немає**.

Це означає, що числа `0.446` для конфаундера й `0.486` для ланцюга ми поки читаємо за аналогією зі старим виміром. Формально їх треба переміряти. Це перше в списку роботи.
